4. CONNAISSANCES NORMATIVES
=====================================

--- DO-178C (Aéronautique) ---

Norme d'orientation pour le développement des logiciels de l'aviation civile.

Conditions de défaillance et niveaux DAL :
  * Niveau A — Catastrophique → perte de vies humaines
  * Niveau B — Dangereux (Hazardous) → blessures graves
  * Niveau C — Majeur → panne affectant le confort des passagers (ex. : climatisation)
  * Niveau D — Mineur → système de divertissement
  * Niveau E — Aucun effet → distributeur automatique

Le niveau DAL est défini par la nature de la défaillance du système.

Stratégies de vérification :
  * Examen (revue)
  * Analyse
  * Test

Documents clés du cycle DO-178C :
  * PSAC — Plan for Software Aspects of Certification
  * SDP — Software Development Plan
  * SSS — System/Segment Specification
  * SRS — Software Requirements Specification (exigences haut niveau)
  * SDD — Software Design Document
  * LLR — Low Level Requirements (exigences bas niveau)
  * Source Code
  * STD — Software Tests Description Document
  * STR — Software Test Results
  * BDD — BITE Description Document (Built-In Test)
  * ICD — Interface Control Document

Processus de vérification :
  - Tests haut niveau (HLT) en face des SRS
  - Tests bas niveau (unitaires) en face des LLR
  - Couverture MC/DC (Modified Condition/Decision Coverage)
  - Couverture sur les décisions et sur les instructions
  - Traçabilité des exigences du système vers les tests

Pour chaque document rédigé, une revue est prévue pour validation.


--- IEC 62304 (Médical) ---

Norme pour le cycle de vie du logiciel des dispositifs médicaux.

Classification par classe de sécurité :
  * Classe A — Pas de blessure ou atteinte à la santé
  * Classe B — Blessure possible mais non grave
  * Classe C — Mort ou blessure grave possible

Appliquée chez : GE Healthcare, Sorin, PK Vitality.


--- MISRA C ---

Norme de programmation en langage C pour les systèmes critiques.
Elle spécifie des règles de programmation pour plus de sûreté.

Objectifs :
  - Éviter des erreurs d'exécution provoquées par des constructions C incertaines
  - Éviter les faiblesses de structure dues aux malentendus entre programmeurs
  - Garantir la validité des expressions

Règles : obligatoires (required), conseillées (advisory), directives.
Outils de vérification : PC Lint, Sonar, Polyspace.


--- ISO 15118 (V2G — Vehicle-to-Grid) ---

Norme pour la communication entre véhicule électrique et borne de recharge.
  * Communication via PLC (Power Line Communication) / HomePlug Green PHY
  * Protocole de charge intelligent (Smart Charging)
  * Échange d'énergie bidirectionnel (V2G)

Appliquée chez : E2-CAD (mission actuelle).


--- OCPP (Open Charge Point Protocol) ---

Protocole de communication entre bornes de recharge et système de gestion central.
Permet le monitoring, la configuration et le contrôle à distance des bornes.


--- Autres normes ---

  * ISO 14443 — Communication sans contact (Smart Card)
  * ISO 15693 — RFID longue distance
  * JSF — Joint Strike Fighter C++ Coding Standard (aéronautique)

5. MÉTHODOLOGIES ET BONNES PRATIQUES
=====================================

--- Cycle en V ---

Processus de développement séquentiel :
  Spécifications → Architecture → Conception → Codage
  → Tests unitaires → Tests d'intégration → Validation

Chaque phase de test correspond à une phase de conception.
Largement utilisé dans l'aéronautique et le médical.


--- Agile / Scrum ---

Méthodologie itérative avec sprints courts (2-4 semaines).
Daily standups, sprint reviews, rétrospectives.
Outils : Jira, Polarion.


--- Jenkins (Intégration continue) ---

Outil logiciel d'intégration continue.
  - Build automatique après chaque commit
  - Exécution automatique des tests
  - Détection rapide des régressions


--- Clean Code ---

Un code compréhensible de façon intuitive et facile à modifier :
  * Le processus d'exécution est logique et structuré simplement
  * Le rapport entre les différentes parties du code est transparent
  * Le rôle de chaque classe, fonction, méthode et variable est immédiatement compréhensible
  * La maintenance est facilitée : les bugs sont trouvés et corrigés facilement

Principes :
  * KISS — Keep It Simple, Stupid (un code aussi simple que possible)
  * DRY — Don't Repeat Yourself (éviter les répétitions inutiles)
  * YAGNI — You Aren't Gonna Need It (supprimer ce qui est inutile)
  * La lisibilité avant la concision

Q : Qu'est-ce que la couverture MC/DC ?
R : Modified Condition/Decision Coverage. Chaque condition d'une décision doit
    indépendamment affecter le résultat de la décision. C'est le niveau de
    couverture le plus exigeant, requis pour le DAL A en DO-178C. J'ai travaillé
    avec la couverture sur les décisions et sur les instructions.

Q : Avez-vous participé aux revues d'exigences ?
R : Oui, chez Thales et Zodiac. J'utilise des check-lists structurées pour
    vérifier la complétude, la cohérence, la traçabilité et la testabilité
    des exigences. Même processus pour les revues de code.

R : Avec Lauterbach TRACE32, je pose des points d'arrêt (breakpoints), j'inspecte
