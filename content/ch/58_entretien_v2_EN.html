5. Methodologies and best practices
V-Model

Specifications → Architecture → Design → Coding → Unit tests → Integration → Validation. Each test phase corresponds to a design phase. Used in aerospace and medical.

Jenkins — Continuous Integration

Automatic build after each commit. Automatic test execution. Rapid regression detection.

Agile / Scrum

Short sprints (2-4 weeks). Daily standups, sprint reviews, retrospectives. Tools: Jira, Polarion.

Clean Code

KISS — keep code as simple as possible
DRY — avoid unnecessary repetition
YAGNI — remove what is unnecessary
Readability over brevity.

7. Common interview questions
Technical questions
Are you familiar with MISRA, JSF, Embedded C rules?
Yes, I applied MISRA C at Safran, Zodiac and Enedis. JSF rules are similar but for C++ in an aerospace context. At Enedis, I used Sonar and PC Lint to verify code compliance.
What is MC/DC coverage?
Modified Condition/Decision Coverage. Each condition in a decision must independently affect the outcome. It is the most stringent level, required for DAL A in DO-178C. I have worked with decision coverage and statement coverage.
Have you participated in requirements reviews?
Yes, at Thales and Zodiac. I use structured checklists to verify completeness, consistency, traceability and testability of requirements. The same process applies to code reviews.
How do you debug on target?
With Lauterbach TRACE32: breakpoints, memory inspection, registers and variables. I complement this with custom logging tools and trace analysis (Wireshark, Saleae).
What is your experience with RTOS?
FreeRTOS at PK Vitality, VxWorks at GE Healthcare, UCOSII and Tnkernel on other projects. I master task management, semaphores, mutexes, message queues and real-time constraints.
What is your embedded Linux experience?
Thales (ATO, LPM, N-MMR), Arkamys (GStreamer), Enedis (Linky), E2-CAD (EV chargers). Application development, Bash scripting, network debugging and cross-compilation with Buildroot.
Behavioral questions
What do you like and dislike about your work?
What I like: the diversity of projects, direct contact with hardware, solving complex problems. What I like less: excessive administrative overhead, but I understand its necessity in certified environments.
Have you ever criticized a colleague's work?
I conduct code reviews in a constructive manner. The goal is to improve the quality of the deliverable, not to criticize the person. I rely on standards and checklists to remain objective.
Can people give you feedback?
Absolutely. Feedback is essential for growth. I welcome remarks as opportunities for improvement. This is the very principle of peer review.
